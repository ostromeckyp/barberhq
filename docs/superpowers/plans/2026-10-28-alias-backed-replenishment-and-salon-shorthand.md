**Goal:** Resolve ordering phrases from authorized SQL catalog/aliases, offer real candidates for unknown wording, and learn removable salon shorthand from a validated explicit choice.

**Architecture:** Keep the current extraction model and request lifecycle. ## Builder decisions for review

1. **Keep persisted normalization stable.** `shared/product-normalization.ts::normalizeProduct` remains byte-compatible with increment 2. Introduce lookup-only `normalizeProductForMatch`, applied to both query and alias/name/type at read time. Otherwise changing shared normalization would reinterpret existing document alias identities and review hashes.
2. **Bound a complete snapshot.** At most 200 catalog products, 5000 eligible global provenance rows before deduplication and 200 active shorthand rows/salon. Read product pages of100, alias pages of1000; fail explicitly on overflow. Unknown wording offers the complete bounded catalog in stable name/ID order and stays a clarification. No second model call for ranking yet.
3. **Bind learning to a server receipt.** Existing clarification input carries wording/choice, but not the extracted productQuery. Issue an opaque receipt for each final clarification; it binds user/business/salon/message hash/span/productQuery/allowed product IDs and expires after10 minutes. Store no full message. Only nonempty product phrases up to120 Unicode characters receive learning receipts; longer phrases still resolve without learning. Old clients without a receipt may still resolve their draft but cannot create shorthand. No additional signing secret or external service.
4. **One confirmation, one salon meaning.** Learn only after valid explicit product and quantity validation, from the receipt's base-normalized productQuery. A newer confirmation replaces the previous mapping only under alias revision CAS. Removing it retires a tombstone rather than deleting revision history; replay cannot resurrect it. Learning is auxiliary: an alias CAS conflict or unavailable write does not invalidate an otherwise valid explicit product choice. Return the verified proposal with a visible NOT_SAVED outcome; do not claim an alias was saved. Membership/product-scope failures still deny preparation. Salon shorthand is language-agnostic for lookup and stores `lang=und`; document generation retains its existing pl/en validation. Other salons and global aliases remain untouched. HQ reads salon shorthand but cannot write it, including when preparing a salon order.
5. **Preserve seed provenance.** Move the existing map into `docs/not-bad-stuff-product-aliases.json`, with reviewed types/keywords. Add nullable `Product.seedType` and bounded `keywords`; projected type becomes latest eligible approved document assertion, falling back to explicit seedType. Source pointer is null for the seed fallback. Publication/withdrawal retain their business snapshot CAS. No seed command overwrites a current document assertion or a salon choice.
6. **Use existing Settings plus a read-only HQ view.** Salon Settings gains a separate shorthand section; its inventory threshold form keeps its own state. HQ gets `/hq/shorthand` with paged salon/phrase/product rows. No bulk remove or unrestricted manual alias editor.

## Review focus

1. A source is withdrawn/replaced or a membership changes between paginated reads and final preparation: no stale alias resolution or learning may commit (Tasks2/3).
2. Two users confirm conflicting meanings for one salon phrase, or an old response is retried after removal: one revision wins, and stale replay never restores an older meaning (Task3).
3. A client fabricates a productQuery or reuses a receipt for another span/message/salon/user: no learned alias and no leaked catalog rows (Task3).
4. Polish stemming collides between products, or NAME/PHONETIC/TYPE rows share a phrase: precedence is explicit and ambiguity remains visible (Task1).
5. A 200-product unknown query reaches the browser: full candidates remain selectable without truncating to six or changing existing manual draft/threshold edits (Tasks3/4).
