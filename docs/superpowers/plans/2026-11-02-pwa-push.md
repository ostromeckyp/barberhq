# PWA and Order Push Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** BarberHQ installs as a PWA on Android and iPhone, and salon users get a push notification when HQ approves, rejects or dispatches their salon's request.

**Architecture:** Angular service worker (ngsw) serves the app shell and also displays pushes and handles notification clicks natively (`notification.data.onActionClick`), so there is a single worker and no custom script. FCM web (`firebase/messaging`) gets a token against the ngsw registration; tokens live in a server-only Data Connect table. The stock command sends via `firebase-admin/messaging` after a non-replayed APPROVE/REJECT/DISPATCH, with a 2 s cap, never changing the command result.

**Deviation from spec (recorded as the spec asks):** the spec proposed ngsw plus an imported custom push script. ngsw already shows `notification` pushes and routes clicks through `data.onActionClick`, and FCM delivers `webpush.notification` in that shape, so no custom script is needed. If manual proof on the iPhone shows no notification, fall back to a custom worker that `importScripts('ngsw-worker.js')` and handles `push`/`notificationclick` itself.

**Tech Stack:** Angular 22.2 (`@angular/service-worker@22.2.0`), Firebase JS SDK 12.19 (`firebase/messaging`), firebase-admin 14.5 (`firebase-admin/messaging`), Data Connect server connector, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-02-pwa-push-design.md`

## Global Constraints

- `AGENTS.md` rules: TDD (failing test first), every user-visible text a Transloco key in both `web/public/i18n/en.json` and `pl.json`, logic files ≤ 300 lines, one exported model per file, web layering route component → facade → data-access → core (components never call Firebase), shared UI reused.
- Never read, print, grep, copy or edit `*.local.json` or `.env`. Structure comes from `config/public.example.json`.
- No production write (deploy, db migration, IAM, console) without the owner's approval for that step. The plan ends at a PR; production steps are listed for the owner.
- Starting emulators regenerates `scripts/generated/browser/index.d.ts` and `web/src/app/core/generated/index.d.ts`; revert with `git checkout --`, never commit.
- Service worker only in the production build (`build:prod`); dev and emulator builds register nothing.
- `commands` keeps `maxInstances: 5`; router App Check behaviour unchanged; approve/reject/dispatch results unchanged.
- Push is only for salon users; sends only on APPROVE → `RESERVED`, REJECT → `REJECTED`, DISPATCH → `DISPATCHED`; never on replay (`CommandResult.replayed === true`).
- Notification `tag` = `request:<requestId>:<state>`; click URL = `/salons/<salonId>/requests/<requestId>`.
- Rejection reason in the body truncated to 100 characters.
- Work on branch `feat/pwa-push` from `main`.

## Review Focus

1. Permission denied, or browser without push (Firefox private, desktop Safari < 16, iPhone Safari not installed): the settings section must show the right state and never throw. Covered by Task 6 facade tests.
2. FCM token rotates or the same device signs in as a different salon user: registering again must move the token to the current user, and sign-out must unregister best effort without blocking sign-out. Covered by Task 4 (upsert moves owner) and Task 6 (sign-out test with a failing unregister).
3. FCM slow or down during a demo click: approve must still return within ~2 s extra and with the same result. Covered by Task 5 timeout test.
4. Stale tokens of users who lost salon access: no push. Covered by Task 4 recipient query joining current `salon_access`, Task 5 test using only returned tokens.
5. A new deploy while the PWA is open: the user sees the reload prompt and gets the new version, and the old worker never serves a broken shell. Covered by Task 3 update-prompt test and `ngsw.json` no-cache check.

**Interfaces:**
- Produces table:
  ```graphql
  type PushToken @table(key: "token") {
    token: String!
    membership: Membership!
    locale: String!
    createdAt: Timestamp! @default(expr: "request.time")
    updatedAt: Timestamp! @default(expr: "request.time")
  }
  ```
- Produces server operations, all `@auth(level: NO_ACCESS)`, called from functions as `sql.<name>(dc, vars)`:
  - `UpsertPushToken($uid: String!, $token: String!, $locale: String!)` — inserts or moves the token to `$uid` and updates locale and `updatedAt`; writes only when a `membership` with `uid=$uid` and `role='SALON'` exists (`@check` → `FORBIDDEN` otherwise).
  - `DeletePushToken($uid: String!, $token: String!)` — deletes the row only if owned by `$uid`.
  - `DeletePushTokens($tokens: [String!]!)` — deletes any of the given tokens (server cleanup of FCM-invalid tokens).
  - `PushRecipients($requestId: String!)` — returns `request { id, state, salonId, salonName, reason }` (reason from the latest REJECT `action_receipt` for the request, else null) and `tokens [{ token, locale }]` of memberships that currently have `salon_access` to the request's salon.
- Follow the `_execute` / `_select` raw-SQL style of `dataconnect/server/salon-alias/*.gql` where a join is needed; table and column names snake_case as there.

  - Texts — en: RESERVED "Request approved", REJECTED "Request rejected", DISPATCHED "Delivery on the way"; pl: "Zamówienie zatwierdzone", "Zamówienie odrzucone", "Dostawa w drodze".   - `notifyRequestState` reads `pushRecipients`; returns early with no tokens or a state outside the three; groups tokens by locale; sends one multicast per locale with:
    ```ts
    { tokens, webpush: { notification: { title, body, icon: '/icons/icon-192.png', badge: '/icons/badge-72.png', tag: `request:${id}:${state}`, renotify: true, data: { onActionClick: { default: { operation: 'navigateLastFocusedOrOpen', url: `/salons/${salonId}/requests/${id}` } } } }, fcmOptions: { link: url } } }
    ```
    Deletes tokens whose response error code is `messaging/registration-token-not-registered` or `messaging/invalid-registration-token` via `deletePushTokens`. The whole call is raced against `timeoutMs`; any error or timeout is logged with `requestId` and swallowed.
  - `stockCommand` change: after `execute` resolves, `if (!result.replayed && ['APPROVE','REJECT','DISPATCH'].includes(type)) await notifyRequestState({ dc, messaging: getMessaging() }, result.requestId)`; the callable returns the same `result`. Notification errors never reach the existing `catch` that maps to `unavailable` (wrap separately).
  - `registerPushToken` input `{ token: string (1..4096), locale: 'en' | 'pl' }` → `{ ok: true }`; `unregisterPushToken` input `{ token }` → `{ ok: true }`; both need auth (`unauthenticated`), invalid input → `invalid-argument`, non-salon user → `permission-denied` (from the `FORBIDDEN` check). Same `region`, `enforceAppCheck`, `maxInstances: 5` options as `stockCommand`.
