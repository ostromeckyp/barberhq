# Product document links and alias review — increment2 implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans inline in the preserved Native mode. Steps use checkbox (`- [ ]`) syntax. One independent final review; no implementer delegation.

**Goal:** HQ links PDF passages to catalog products, generates and reviews proposed aliases, and activates the accepted knowledge only when the document version is published.

**Architecture:** Extend the existing SQL Connect document lifecycle with version-bound product links, product profiles and alias proposals. Server-controlled Genkit calls propose data; HQ and native GraphQL transactions decide what becomes active. Product type is a projection of eligible, explicitly reviewed source assertions, with source-aware retirement.

**Tech Stack:** Existing Angular22.2/Material, Firebase Auth/App Check, SQL Connect/PostgreSQL, Cloud Functions/Tasks, Genkit1.42.0 and the existing Vertex Gemini runtime. No new dependency.

**Spec:** [Product knowledge and dictated replenishment](../specs/2026-10-24-product-knowledge-and-dictated-replenishment-design.md), increment2 and Decisions. Increment1 is implemented locally: [handoff](../../implementation/knowledge-kind-origin.md). Its cloud rollout remains pending.

**Authority/status:** Owner requested continuing with expansion after increment1. This plan translates the existing product-document design into an implementation sequence; builder decisions below are proposals for this plan review. No product source code, schema or cloud data changes are authorized by writing this file. Execute after owner review using the existing Native preference.

## Global constraints

- Retain the existing stack, server-derived business scope, Firebase Auth/revoked-token checks and App Check. Only HQ may view or modify unpublished links/proposals; SALON never receives drafts.
- Every AI request retains25 seconds,5 model turns and8 tool calls. Use the existing shared10 admissions/user/UTC-hour counter; do not create a separate quota or silently reset a budget inside a document loop.
- One alias-generation model call per linked product. Each is an explicit, individually retryable HQ action. Code matching is deterministic; a name-based link suggestion is a separate optional single-section AI action, always confirmed by HQ.
- Product names, source codes, types, traits, aliases and phonetic examples come from scoped data. No new product-specific logic or prompt examples. Existing hard-coded replenishment matching is replaced in increment3, not here.
- Generated product links, types and aliases are proposals. No automatic publication, stock mutation, substitution, global alias learning, microphone or replenishment behavior change in this increment.
- Preserve PDF bytes/hashes/generations, page/chunk IDs, geometry, embeddings, citation URLs, document review history and existing request/receipt workflows. Product references remain eligible for procedure RAG.
- Retain dirty/staged owner checkout and pre-existing compact-login work. No commit/stage/push, dependency reinstall, workspace cleanup, owner emulator reset, deployment, cloud fixture creation or live provider invocation. Local disposable services use controller-owned ports and native PostgreSQL17/pgvector, not the failing PGlite path.
- Never access private environment/configuration files; use examples or explicitly allowed public snapshots. Update the code-review graph after source changes; absence from its index is not evidence of no dependency.

## Builder decisions for review

1. **Reuse the document review screen.** Add Product knowledge below the existing PDF/text review: source passage, linked product, editable proposed type/aliases and collision impact. Existing physical-page review remains required. Procedure/policy flow is unchanged.
2. **Edit unpublished versions only.** Existing published PDFs remain immutable. To enrich the current published catalog, create its next ordinary version with the same PDF bytes and review it. No silent reprocessing or backfill of published product knowledge. Local acceptance uses disposable catalog versions; any live replacement requires separate approval.
3. **Anchor exact passages.** A passage is `{chunkId,start,end}` using UTF-16 offsets into the stored chunk text, bound to version/extractionHash. Chunks may contain several products: never attach a whole multi-product chunk to one product by guessing. HQ can use a whole section or paste an exact, uniquely located excerpt to narrow it; ambiguous repeated text needs an explicit occurrence selection. No rechunking.
4. **Keep provenance per source.** Identical aliases for the same product from two documents are separate rows. Eligibility deduplicates phrases/products, not provenance. Withdrawing one source retires only its rows. Manual aliases added during this review have sourceHQ and the same document-version dependency; independent manual alias administration belongs to a later scope.
5. **Product type remains explainable.** Store a reviewed type assertion per version/product. `Product.type` and its source-version pointer reflect the latest eligible approved non-null assertion, ordered by server publication time then version ID. Replacement/withdrawal recomputes the affected products in the same transaction. Show the old/new type explicitly before HQ accepts it; no hidden last-writer overwrite.
6. **Bound and resume work.** Maximum200 catalog products,200 linked passages/version,32 alias proposals/product,120 Unicode characters/phrase,80/type, languagespl/en. Model input: at most16000 source characters/product and64000 serialized catalog/active-alias characters; output at most2048 tokens. Read catalog through pages of100 and eligible business-global alias provenance through pages of1000, at most5000 alias rows before deduplication; fail explicitly on overflow; never silently truncate a catalog or source into a wrong suggestion. A larger document can still be a read-only PDF reference; it needs a later scaling plan for alias processing.
7. **Incomplete AI is recoverable.** HQ can link, edit and reject manually without a provider call. A product card requires exactly one distinct confirmed product; a catalog may leave explicitly acknowledged passages unlinked, producing no aliases. All generated candidates need an explicit accept/reject decision before product review is final. A null proposed type means no new type assertion, never an invented default.

## Review focus

1. A catalog chunk mentions two products or repeated section headings: source passages and product facts must not leak across links (Tasks1/2/3 tests).
2. A model call finishes after a link/source/catalog edit or access revocation: reject stale output, retaining reviewed manual work (Tasks2/3).
3. Another HQ publishes the same phrase for another product while review is open: refresh collision impact and require a new acknowledgement; never publish using stale review state (Task4).
4. Two current documents support the same alias, or a type-provider document is withdrawn: surviving provenance remains active and type projection follows the remaining source (Task4).
5. A publication response or worker acknowledgement is lost: retry preserves document review key/hash and frozen product-review identity; no duplicate aliases, partial activation or lost stock (Tasks2/4/5).
